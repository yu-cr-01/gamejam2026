## 5. Git 协作规范

### 5.1 分支策略

```text
main                ← 只放「可运行」的版本，受保护，不直接 push
  │
  └── develop       ← 集成分支，功能合并到这里
        │
        ├── feature/player
        ├── feature/enemy
        ├── feature/ui
        ├── feature/level
        └── feature/vfx
```

| 分支 | 规则 |
|---|---|
| `main` | **只接受来自 `develop` 的合并**；每次合并必须打 Tag；永远处于可运行状态 |
| `develop` | 功能完成后合入；每天至少保持一次「可运行」 |
| `feature/*` | 个人工作分支，命名 `feature/<模块>-<简述>` |
| `fix/*` | 紧急修复，修完立即回合 |

### 5.2 提交规范

格式：`<type>(<scope>): <描述>`

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 Bug |
| `art` | 美术资源 |
| `audio` | 音频资源 |
| `refactor` | 重构（不改行为） |
| `perf` | 性能优化 |
| `docs` | 文档 |
| `chore` | 构建 / 配置 / 杂项 |

示例：

```text
feat(player): 实现 WASD 移动与摄像机跟随
fix(ui): 修复血量条在低分辨率下错位
art(env): 导入灯塔场景模型与贴图
chore: 忽略 Builds/ 与 Logs/ 目录
```

### 5.3 合并规则

- [ ] 合并前：**自己本地跑通一遍**，不要让别人当你的测试机
- [ ] 合并前：先 `git pull --rebase` 拿最新 `develop`
- [ ] 冲突集中在 **Scene / Prefab** 时：优先找该资源负责人一起处理，**不要强行覆盖**
- [ ] 每天至少提交一次（哪怕只是进度）
- [ ] 最后 3 天冻结 `develop`，只允许 `fix/*` 合入

### 5.4 禁止事项

- ❌ 提交 `Library/`、`Temp/`、`Logs/`、`obj/`、`Builds/`、`.csproj`、`.sln`
- ❌ 直接覆盖别人的工作（`git push --force` 到共享分支）
- ❌ 不打招呼改核心架构 / 公共接口
- ❌ 最后一天才第一次打包测试
- ❌ 因为「以后可能用到」无限加功能

## 8. TA 流程

### 8.1 TA 职责范围

TA 不只是「帮忙做特效」。

- [ ] Shader 编写与优化
- [ ] VFX 制作
- [ ] Material 规范与统一
- [ ] 美术资源导入规范（压缩、图集、LOD、导入设置）
- [ ] Prefab 制作与维护
- [ ] 参数暴露（让策划/美术能在 Inspector 调，不用改代码）
- [ ] 技术验证（这个效果在当前管线/性能下能不能做）
- [ ] 性能优化（Draw Call、Overdraw、内存）
- [ ] 工具开发
- [ ] 美术与程序之间的衔接

### 8.2 工作流

```text
策划需求
   ↓
TA 拆技术方案        ← 判断可行性，给实现路径
   ↓
快速 Prototype       ← 用最糙的方式验证「能不能做出来」
   ↓
程序接入             ← 对接游戏逻辑
   ↓
美术补资源           ← 替换正式资源
   ↓
TA 整合              ← 统一材质 / 参数 / 表现
   ↓
优化                 ← 性能与观感
   ↓
最终效果
```

### 8.3 TA 第一优先级（21 天版）

- [ ] **不要一开始就做复杂工具** —— 工具是省时间的手段，不是目的
- [ ] **先让核心效果跑起来**，哪怕用最丑的占位资源
- [ ] 能参数化的参数化（策划能在 Inspector 调，就不用每次找程序）
- [ ] 能复用的做成 Prefab / Material / ScriptableObject
- [ ] 性能问题**留到 Alpha 之后**统一处理，不要过早优化

## 9. 策划框架

### 9.1 GDD 存放位置

`docs/GDD.md` —— 主文档。**一句话介绍 + 核心循环**必须最先写，其他可以边做边补。

### 9.2 GDD 最小清单

- [ ] 游戏一句话介绍
- [ ] 核心玩法
- [ ] **核心循环**（见 §9.3）
- [ ] 玩家目标
- [ ] 游戏规则
- [ ] 胜负条件
- [ ] 关卡流程
- [ ] 玩家成长
- [ ] 数值
- [ ] UI
- [ ] 音频
- [ ] 美术需求
- [ ] 技术需求

### 9.3 核心循环（必须画清楚）

```text
玩家做什么
   ↓
得到什么反馈
   ↓
获得什么奖励 / 结果
   ↓
产生什么新的挑战
   ↓
继续下一轮
```

> 如果这个循环三句话说不清，说明玩法还没想清楚，不要开工。

### 9.4 MVP 分级

| 级别 | 含义 | 处理 |
|---|---|---|
| **P0** | 没有它游戏就不能玩 | 必须先做完 |
| **P1** | 有了更好，明显提升体验 | P0 全绿后再做 |
| **P2** | 时间够再做 | Alpha 之后评估 |

> **原则：先完成 MVP，再追求表现。**

## 10. 任务管理系统

### 10.1 看板

```text
Backlog  →  Todo  →  Doing  →  Review  →  Done
```

| 列 | 含义 |
|---|---|
| Backlog | 想法池，未排期 |
| Todo | 已排期，有负责人和截止时间 |
| Doing | 正在做（**同时最多 1~2 项**） |
| Review | 做完待验收（由模块负责人验收） |
| Done | 已验收并合入 `develop` |

### 10.2 任务卡片模板

每个任务**必须**包含：

```text
任务：<名称>
负责人：<唯一负责人>
优先级：P0 / P1 / P2
截止：<日期 时间>
依赖：<依赖的任务，没有就写「无」>
交付物：<具体产出，如 P_Player.prefab>
验收标准：
  □ <可验证的条件1>
  □ <可验证的条件2>
  □ 可打包运行
```

### 10.3 拆解粒度

❌ 不要写：

> 做战斗系统

✅ 拆成：

```text
玩家攻击
敌人受伤
伤害计算
死亡
掉落
战斗 UI
```

> **每个任务控制在「一个人 0.5 ~ 1 天能做完」的粒度。**

### 10.4 示例卡片

```text
任务：玩家移动
负责人：程序A
优先级：P0
截止：10/02 14:00
依赖：无
交付物：P_Player.prefab + PlayerController.cs

验收标准：
  □ WASD 移动
  □ 摄像机跟随（无抖动）
  □ 不穿墙
  □ 可打包运行
```
