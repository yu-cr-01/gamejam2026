# 规则逻辑架构（卡牌 v2.1）

> 给**不看代码的人**看：这套逻辑怎么搭、为什么这么搭、现在能跑到哪一步。
> 数据正文：`卡牌需求设计_v2.1.md`（卡表）、`卡牌规则_v2.1_飞书原文.md`（策划书总结 v3，规则主体）
> 数据文件：`Resources/Config/cards_v21.json`　代码：`Assets/Scripts/Rules/`　离线自测：`Tools/RuleProbe/run.ps1`

---

## 一句话

**策划写中文规则 → 代码把该解析的解析成"操作"、该查表的走硬编码规则表 → 一回合按固定顺序结算 → 每一步都留中文日志。**

两种规则来源要分清（这是这套架构最关键的一条分工）：

| 规则来源 | 谁说了算 | 例子 |
|---|---|---|
| **硬编码规则表** | 程序员按表实现 | 附魔规则表：热≥1 且目标易燃 → 燃烧，D 立即归零 |
| **卡牌自带文本** | 策划改 JSON 就生效 | 某张卡的「启动 / 献祭」那一两行 |

形态转换**不走文本解析**，一律查附魔规则表（层数 × 目标标签）；卡牌文本只负责这张卡**自己**的启动/献祭效果。

## 四层结构

```
┌─ 1. 数据层（策划改这里）
│    docs/卡牌需求设计_v2.1.md / docs/卡牌规则_v2.1_飞书原文.md   人看的正文
│    Resources/Config/cards_v21.json                             结构化数据（31 素材 + 8 法术）
│
├─ 2. 状态层（"现在是什么样"）
│    LayerLedger    刀片上的四种附魔：热/冷/酸/催化，每种分"会衰退 / 不衰退"两份计数
│    BladeState     刀片：H（≤0 就是爆刀）+ V（计分用）+ 附魔层数
│    MaterialState  桌面上一张素材：卡本身 + D（耐久，归零 = D 耗尽）+ 当前形态
│
├─ 3. 规则层
│    EnchantRules   附魔规则表（热 7 条 / 冷 5 条 / 酸 5 条 + 催化阈值修正），按优先级只触发最高一条
│    RuleText       解析卡牌自己的「启动 / 献祭」文本 → 条件 + 操作；解析不了的进「未识别清单」
│
└─ 4. 结算层（"一次启动怎么走"）—— TurnEngine，顺序照正文，一步不改
     ① 消耗 1 行动机会 + 1 刀片H
     ② 按 热→冷→酸→催化 查附魔规则表，每种只触发最高优先级一条
     ③ 形态变化/溶解移除 → 旧卡移出桌面、新卡进手牌、新卡 D 重置为满，本次不再 D−1
     ④ 未形态变化 → 目标 D−1；D≤0 走 D 耗尽（产法术 + 副产物；没有产物就产空白卡）
     ⑤ 计分 = 目标素材V + 刀片V（目标已移除则用启动时的原始 V），即时入总分
     ⑥ 查爆刀：H≤0 → 立即爆刀、关卡结束、**当前分数 ×2**
     ⑦ 若这是本回合**实际最后一次启动**且目标仍有 D → 献祭吞噬（刀片 H+=卡H、V+=卡V）
     回合末：所有附魔层数 −1、归零消失；桌面素材保留
```

## 为什么这么分（几条踩出来的经验）

**① 层数的约定只能有一处。**
「不衰退」的意思是：不随回合衰减、不因启动减少，但**会被"消耗所有 X 层数"消耗**（卡表备注原话）。
如果让每张卡各写各的（`heat++`），这条约定就会散落到几十处。现在加层/消耗/衰减/覆盖只有几个入口，
全在 `LayerLedger` 里，改一处就全变。

**② 冷热冲突是"覆盖"，不是"对消"。**
卡表备注写的是"冷热之间会按照规则互相抵消"，我先按**成对抵消**实现了；
读完正文才知道"规则"指规则表 F 的「**后附魔覆盖先附魔，清空对方全部层数**」——
先有热×1，再打冰霜（冷×1）→ 结果是冷×1、热清零，而不是两边都归零。
这条已经改掉，并且写进了离线断言，防止以后再改回去。

**③ 规则要么能跑，要么明说不能跑。**
卡牌文本是中文，解析必然有认不出的写法。**最坏的情况不是"没实现"，而是"看起来实现了其实没生效"** ——
所以解析失败的句子一律进「未识别清单」（哪张卡、哪个字段、原句），界面上也能查。

**④ 结算顺序写死在一处，而且可解释。**
"启动 → 查附魔 → 转换/移除 → D → 计分 → 爆刀 → 献祭"这个顺序是正文规定的，
写在 `TurnEngine` 一处，每一阶段都打中文日志 —— 玩家说"我明明这么打却没过"时，能一条条对回去。

| 卡牌文本解析（启动/献祭）+ 未识别清单 | ✅ 已实现 |

| 卡牌总览界面（看全部素材/法术与卡面） | ✅ 游戏里按 **F1** |
| **接进 3D 桌面的回合循环** | ❌ 还没接：`TableTurnLoop` 现在跑的还是旧模型（H/D/V 数值 + 杯内粒子模拟） |

### "还没接"是什么意思
现在这套是**独立的、可离线验证的规则内核**：给它刀片状态和桌面素材，它能算出这次启动发生什么、得多少分。
它还不知道怎么跟 3D 桌面上的"拖牌 → 启动破壁机 → 冲压"对接。对接要做的事：
回合结算改调 `TurnEngine`、杯内食材改用 `MaterialState`、刀片改用 `BladeState`、行动机会与回合数接进 `Level/TurnState`。
这一步会动现有玩法代码，建议单独分支做。

## 正文里自相矛盾、需要策划拍板的地方

| # | 冲突 | 现在的处理 |
|---|---|---|
| 1 | **启动是否消耗附魔层数**：2.4 节与「七-7」说"启动不消耗"，规则表 F 说"启动时无论是否发生效果，消耗 1 层" | 做成开关 `TurnRules.ConsumeLayerOnActivate`，默认**按规则表 F 消耗 1 层** |
| 2 | 「性质标签·献祭」与机制「献祭吞噬」同名不同物 | 代码里分别叫 `TagSacrifice`（标签）与 `DevourOnLastActivate`（机制） |
| 3 | 规则表字母 E、F 各重复用了一次（E 催化 / E 形态、F 阈值 / F 衰减） | 按小节标题区分，不影响实现，建议策划改成 G/H |
| 4 | 2.2 定义 D≤0 触发 D 耗尽，规则表 B-1「燃烧：目标 D 立即归零」也直接走 D 耗尽 | 两者都按"D 归零 → 走 D 耗尽产物"处理 |
| 5 | 「每回合结束所有附魔 −1」与卡表的"不衰退层" | 普通层 −1；卡牌明确写"不衰退"的那份不动 |
| 6 | 催≥3 再 −1「当前 Demo 不开放」 | 规则已实现，用开关控制是否启用 |

正文没写数值的地方（例如汞蒸气「每消耗一层获得一定分数」），集中放在 `TurnRules` 里，改一处即可。
