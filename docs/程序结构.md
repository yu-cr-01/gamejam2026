# 《破壁机计划》程序结构

> 这份文档说明**代码是怎么分的、为什么这么分**。
> 玩法规则和数值请看 `开发文档.md`，这份只管结构。

---

## 一、分层

```
                       Resources/Config/game_config.json
                                    │
                          ConfigDto（DTO，扁平，跟 JSON 一一对应）
                                    │
                          GameConfig（唯一的翻译层）
                                    │
        ┌───────────────────────────┴───────────────────────────┐
        │                     Data/  —— 运行时数据               │
        │  属性 · 效果 · 食材 · 牌组 · 变速模块 · 选择 · 关卡      │
        │  这一层**不依赖任何渲染**，也完全不认识"谁来画它"        │
        └───────────────────────────┬───────────────────────────┘
                                    │
                          Sim/ —— CupSim（纯逻辑模拟）
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
   Prototype/                  Table/                      Board/
   （Flow2D 文字原型）         （Table3D 桌面原型）         （Board2D 棋盘原型）
```

**依赖方向是单向的**：表现层可以读数据层，数据层永远不知道表现层存在。
这条是硬约束 —— 一旦反过来（比如 `Ingredient` 里出现 `Renderer`），
三套原型就没法共用同一份数据，换画法就得重写规则。

## 二、Data/ —— 四条解耦线

数据层按**变化的原因**切分，不是按"哪个界面用到"切分。

### 1. 属性 —— `Attributes/`

| 文件 | 职责 |
|---|---|
| `AttrId.cs` | 三个属性的枚举：Salt(盐性) / Mercury(汞性) / Sulfur(硫性) |
| `AttrDef.cs` | 单个属性的定义：字母、显示名、倾向、说明、格式化 |
| `AttrCatalog.cs` | 属性总表。**加一个属性只改这里** |
| `AttrSet.cs` | 一整套数值（定长数组，下标 = `(int)AttrId`） |

`AttrSet` 单独成一个类，是为了让**效果只依赖"一个数值容器"**，
不关心它属于食材、刀片还是杯子。`ResolveAttrs` 能作用在任何 `AttrSet` 上。

> 为什么不用 `Dictionary`：Unity 不能序列化 Dictionary。

### 2. 效果 —— `Effects/`

| 文件 | 职责 |
|---|---|
| `EffectOp.cs` | 运算方式：加 / 减 / 百分比 / 设为 |
| `Effect.cs` | 一条效果：对哪个属性、怎么算、算多少 |
| `EffectGroup.cs` | 效果的**组合**，靠 `Append` 叠加 |

这一层单独抽出来的**目的是并发**：多张牌同时发动时，
效果是靠 `EffectGroup.Append` 一层层叠进同一个 `activeEffects`，
而不是各改各的数值。

> ⚠️ 这条是踩过坑的：`TableTurnLoop` 一开始写了"每回合只能投一张"，
> 等于从界面层把整套效果组合体系掐死了。规则现在放开成每回合两次行动。

### 3. 选择 —— `Choices/`

| 文件 | 职责 |
|---|---|
| `Choice.cs` | 一次选择：给若干候选、挑 N 个 |
| `ChoiceOption.cs` | 一个候选项（只存展示信息 + 引用 id） |
| `ChoiceView.cs` | **界面形态**：列表 / 牌组卡 / 换刀片 |
| `ChoiceRecord.cs` | 一次选择的结果 |
| `SelectionLog.cs` | 玩家做过的全部选择 |

关键设计：**关卡声明自己有哪些选择环节，状态机不认识"牌组""刀片"这些业务概念。**
`ChoiceView` 让"画成什么样"成为数据的一部分 —— 想加第三个环节（比如选模块），
在配置里追加一条就行，不用动状态机。

`SelectionLog` 和 `TurnState` **互不依赖**：
前者管"玩家做过什么选择"，后者管"现在场上是什么"。

### 4. 关卡 —— `Levels/`

| 文件 | 职责 |
|---|---|
| `LevelData.cs` | 这一关**是什么**：id、名字、目标分、自带的选择环节、关卡规则 |
| `Level.cs` | 这一关**现在怎么样了**：进行状态、打了多少分、开过几次 |

```csharp
LevelData  —— 配置，可 Clone、可存盘，一局里不变
Level      —— 运行时，持有 TurnState，有 Ready/Playing/Cleared/Failed/Abandoned 状态
```

混在一起的话，想重开一关就得把定义也重建一遍，运行时状态会污染配置。

`Level.passByDefault` 现在是 `true` —— 数值模拟还没接、得分恒为 0，
严格按分数判定会让流程死在第 1 关。等模拟落地关掉即可。

### 5. 会话 —— `Session/TurnState.cs`

一关之内的过程数据：手牌 / 变速模块 / 刀片 / 杯内食材 / 得分 / 本局效果组合。

**它挂在 `Level` 上，不挂在界面上。** 一开始它飘在 `TableTurnLoop` 里，
等于"这条命是谁的"没有主 —— 退出关卡时该丢掉的东西丢不干净。
`TableTurnLoop.turn` 现在是个转发属性（`get => level.turn`），不是又存了一份。

## 三、Sim/ —— 模拟内核

| 文件 | 职责 |
|---|---|
| `Sim/CupSim.cs` | 粒子运动、温度、刀片磨损、反应判定、飘字。**一条渲染都不做** |

分层的理由很实际：这堆规则是策划要反复调的，渲染是美术的事。
混在一起的话，调一个数值也要先看懂半屏画法。

### 关键决定

**① 随机源是自己实现的 xorshift32，不用 `UnityEngine.Random`**

两个原因，第二个才是要命的：

1. 它是引擎的内部调用（ECall），离开 Unity 进程直接抛异常
2. **它没有种子、结果不可复现** —— 玩家说"我明明这么打却没过"时根本没法回放

好处是模拟可以脱离 Unity 单独跑测试（见第六节）。

**② 反应规则是数据（`ReactionDef`），不是代码**

用"阈值与"表达：汞性 ≥ 8 且 盐性 ≥ 5 → 乳化。
整条规则就是一串数字，将来挪进配置表直接能用。

**③ 坐标一律归一化**

中心 `(0.5, 0.5)`、内壁半径 `0.44`。
换分辨率、换面板尺寸都不用改 `CupSim` 里任何一个数字。

## 四、表现层 —— 三套并行

`PrototypeMode.Current` 决定启用哪一套，三套**共用同一份 Data 和 Sim**。

| 目录 | 原型 | 形态 |
|---|---|---|
| `Prototype/` | Flow2D | IMGUI 纯文字流程，用于验证状态流转 |
| `Table/` | **Table3D** | 3D 桌面（当前主线） |
| `Board/` | Board2D | 2D 棋盘 |

Table3D 和 Board2D **不是新旧版本，是同一玩法的两种画法**，随时可以来回切。

### Table3D 的装配与驱动

```
TableSetup.Awake()                     ← 全部用代码搭，场景文件保持空的
  ├─ BuildCamera / BuildLights / BuildTable / BuildSlots
  ├─ BuildRoots / BuildJuicer
  ├─ BuildTurnLoop          → TableTurnLoop（只建组件、接引用，还不开始）
  ├─ BuildInteraction       → TableInteraction + TableHud
  ├─ BuildChoiceRig         → TableChoiceRig
  ├─ BuildTitleRig          → TableTitleRig
  └─ turnLoop.Begin()       ← ★ 最后才开始
```

`Begin()` 必须放最后：它一执行就进开场界面，
那时候桌面、HUD、交互、开场 rig 必须都已经就位。顺序动过就会踩空。

**`TableTurnLoop` 是唯一的驱动源**，它持有 `Level`，按阶段机推进：

```
Title → LevelSelect → DeckPick → BladePick → Select → Simulating → TurnResult
                                                          ↕              │
                                                    LevelEnd ←───────────┘
                                                          ↓
                                                    LevelResult
```

### 表现层的分工

| 文件 | 管什么 | 不管什么 |
|---|---|---|
| `TableSetup.cs` | 搭场景、发牌 | 规则、阶段 |
| `TableTurnLoop.cs` | 阶段机、投放、回合推进 | 怎么画 |
| `TableInteraction.cs` | 射线拾取、拖拽、吸附 | 是否允许拖（问 turnLoop） |
| `TableHud.cs` | 所有 IMGUI 面板 | 数据 |
| `TableChoiceRig.cs` | 牌组 / 刀片 / 关卡的 3D 卡片 | 选择规则 |
| `TableTitleRig.cs` | 开场的书 / 木牌 / 蜡烛 | — |
| `CupSimView.cs` | 杯内 2D 视图 | 模拟规则 |
| `CardFactory.cs` | 造一张 3D 卡 | 谁在拖它 |
| `ProceduralArt.cs` | 程序化贴图（卡面、圆、辉光…） | — |
| `JuicerRig.cs` | 榨汁机建模 + 冲压动画 | 得分从哪来 |
| `CameraRig.cs` | 机位、自由转头锥形约束 | — |

### 手牌的唯一来源

`TableSetup.DealHand()` **只负责把 `TurnState` 画出来**，不自己读牌组。

> 踩过的坑：原来它自己调 `deck.InitialHandIngredients()`，
> 于是桌面上摆的牌和 `TurnState` 里记的牌是两份互不相干的数据，
> 而且那份实现漏掉了变速模块 —— 模块永远进不了玩家手里。

## 五、配置边界

```
game_config.json  →  ConfigDto  →  GameConfig  →  Data 运行时对象
```

**DTO 和运行时对象分开**：运行时对象挂着一堆 `[NonSerialized]` 引用、
用 `AttrSet` 定长数组存属性，不适合直接写进给策划看的表。
DTO 是扁平的、字段名和 JSON 一一对应。

好处：**策划改 JSON、程序员改 DTO，两边结构永远一致。**

`GameConfig` 是唯一读配置的地方，且**只往外给克隆**——
调用方会往 `LevelData` 上挂运行时状态，直接给出去的话第二次读到的就是被改过的配置。

## 六、验证工具

| 工具 | 位置 | 用途 |
|---|---|---|
| `AutoPlayHarness` | `Assets/Editor/` | 命令行自动进 Play，可自动走完整个流程并截图 |
| `TablePreviewCapture` | `Assets/Editor/` | 编辑模式下 `Camera.Render()` 出图 + 命中测试 |
| `SimProbe` | `Tools/SimProbe/` | **不开 Unity** 的 CupSim 规格校验 |

`SimProbe` 之所以能脱离 Unity，正是因为 `CupSim` 是纯逻辑、
只用 `Vector2`/`Mathf` 这些 CoreModule 里的数学类型。
它把数据层 + `CupSim` 编成控制台程序直接跑，
**不占工程锁、不用等编辑器启动**。

> 这一点在协作里很关键：编辑器一旦被占用，就起不了第二个实例跑自动化。
> 所以"能不能脱离 Unity 验证"是分层时要主动争取的性质。

## 七、几条踩出来才有的约定

| 约定 | 为什么 |
|---|---|
| 卡面文字只放 `localZ ≤ 0` | 正半区的文字完全不渲染，根因没查到，规律先记着 |
| `CardFactory.AddText` 高度要显式传 | 卡牌厚度不统一（手牌 0.008 / 牌组卡 0.018），用默认值字会被埋进卡身 |
| 销毁一律走 `CardFactory.DestroySafe` | 编辑模式下 `Object.Destroy` 会报错，而 `TablePreviewCapture` 就是在编辑模式跑 Awake |
| IMGUI 不要用 `FontStyle.Bold` 配中文字体 | 雅黑没有独立粗体字面，伪粗体把中文糊成双影 |
| 每帧覆盖的值（如火焰尺寸）只写一份常量 | 建模和抖动各写一份的话，改建模那处不生效还不知道为什么 |
| `ScreenCapture` 不可靠，优先 `Camera.Render()` | 显示器被全屏程序占住时它会**静默失败**：日志说截了，磁盘上没有 |
| 截图和改状态不能在同一帧 | `CaptureScreenshot` 帧末写盘，同帧改状态会拍到改完之后那一帧 |

## 九、当前状态与未接的部分

**已接**：开场 → 关卡界面 → 选牌组 → 选刀片 → 回合循环 → 杯内模拟 → 回合结算 → 下一关。

**未接**：

- 数值模拟的**真实反应数值和磨损速率**（现在是按飘字样例反推的占位值，
  改 `ReactionCatalog` 即可，不用动 `CupSim`）
- 关卡之间**内容没有区分**（三关除了目标分完全一样；
  `LevelData.WithRules` 这个接口一直有但还没人用）
- 变速模块**还没接进转速**（`CupSim.bladeSpeed` 目前恒为默认 60°/秒）
- 存档、音量等设置项（`TableSettings` 是壳子，挂了三项能用的）
