Game Jam 首次组会 TodoList

21 天限时创作 · 团队生产管线搭建清单

会议时长：45～60 分钟 核心目标：主题公布前，把管线先搭好

一、团队基本信息

1. 确定工作室 / 队伍名称

  • 队名 / 工作室名
  • 英文名（如需要）
  • Logo / 头像
  • 队伍介绍一句话
  • 确定队长
  • 确定对外统一使用的名称

2. 确定团队目标

  • 这次 Game Jam 想做到什么程度？
  • 第一目标：完成一个完整可玩的游戏
  • 第二目标：作品质量 / 技术亮点
  • 第三目标：作品集 / 后续继续开发
  • 明确原则：先完成 MVP，再追求表现

二、确定技术栈

3. 游戏引擎

  • Unity
  • 确认 Unity 具体版本
  • 所有人安装相同版本
  • 确认渲染管线：Built-in / URP / HDRP
  • 确定使用的插件
  • 确认插件版本
  • 不允许个人私自更换核心版本

4. 开发工具

  • Visual Studio / Rider
  • Git
  • GitHub / Gitee / GitLab
  • Discord / QQ / 微信群 / 飞书
  • Notion / 飞书多维表格 / Trello / GitHub Projects
  • 网盘备用

三、确定“怎么共享开发”

5. 代码协作

  • 建立 Git 仓库
  • 配置 Unity .gitignore
  • 所有人 clone 项目
  • 所有人成功运行项目
  • 测试一次 Pull / Commit / Push
  • 测试一次分支合并
  • 确定 Git 分支策略

建议：

main
  │
  ├── develop
  │
  ├── feature/player
  ├── feature/enemy
  ├── feature/ui
  └── feature/system
  • main 只放可运行版本
  • 每个人尽量在自己的 feature 分支工作
  • 完成功能后合并
  • 合并前自己测试
  • 每天至少提交一次

6. Unity 资源协作

  • Scene 谁负责
  • Prefab 谁负责
  • Script 谁负责
  • VFX 谁负责
  • Materials 谁负责
  • ScriptableObject 谁负责
  • 避免多人同时修改同一个 Scene / Prefab
  • 确定资源命名规范
  • 确定目录结构

建议：

Assets/
├── Art/
├── Characters/
├── Environment/
├── VFX/
├── Materials/
├── Audio/
├── Prefabs/
├── Scenes/
├── Scripts/
├── UI/
└── Resources/

7. 电脑 / 编辑器共享

  • 平时以 Git 为主
  • 需要一起写代码时使用 Live Share
  • 看 Unity 编辑器 / Game View 时使用 Discord / 腾讯会议共享屏幕
  • 不把 Live Share 当 Git 替代品

四、美术资源怎么做

8. 确定美术生产渠道

讨论并确定主要来源：

  • 自制
  • 免费开源素材
  • 商用素材包
  • AI 辅助生成
  • Blender / Photoshop / Krita / Substance Painter
  • Asset Store
  • 其他资源站

9. 美术资源管理

  • 所有第三方素材记录来源
  • 记录许可证 / 商用授权
  • 记录下载链接
  • AI 生成素材做好记录
  • 确定最终哪些资源进入游戏
  • 不允许随便使用来源不明素材

10. 美术风格统一

  • 整体画风
  • 色彩方向
  • 光照方向
  • UI 风格
  • VFX 风格
  • 模型风格
  • 是否使用统一参考图

最好在第一天建立：

Art Bible / 美术规范

哪怕只有一页。

五、TA 流程怎么做

11. TA 负责什么

TA 不应该只是“帮忙做特效”。明确 TA 的职责：

  • Shader
  • VFX
  • Material
  • 美术资源导入规范
  • Prefab 制作
  • 参数暴露
  • 技术验证
  • 性能优化
  • 工具开发
  • 美术与程序之间的衔接

12. TA 工作方式

建议：

策划需求
↓
TA拆技术方案
↓
快速 Prototype
↓
程序接入
↓
美术补资源
↓
TA整合
↓
优化
↓
最终效果

13. TA 第一优先级

  • 不要一开始就做复杂工具
  • 先让核心效果跑起来
  • 能参数化的参数化
  • 能复用的做成 Prefab / Material / ScriptableObject
  • 后期统一处理性能

六、策划框架怎么建立

14. 游戏设计文档

建立一份最小 GDD：

  • 游戏一句话介绍
  • 核心玩法
  • 核心循环
  • 玩家目标
  • 游戏规则
  • 胜负条件
  • 关卡流程
  • 玩家成长
  • 数值
  • UI
  • 音频
  • 美术需求
  • 技术需求

15. 核心循环必须写清楚

玩家做什么
↓
得到什么反馈
↓
获得什么奖励 / 结果
↓
产生什么新的挑战
↓
继续下一轮

16. MVP

必须明确：

  • 什么是“没有它游戏就不能玩”
  • 什么是“有了更好”
  • 什么是“时间够再做”

分成：

P0：必须做
P1：应该做
P2：有时间再做

七、任务怎么下发

17. 建任务看板

建议使用：

Backlog
↓
Todo
↓
Doing
↓
Review
↓
Done

18. 每个任务必须包含

  • 任务名称
  • 负责人
  • 截止时间
  • 优先级
  • 依赖项
  • 最终交付物
  • 验收标准

例如：

任务：玩家移动

负责人：程序A
优先级：P0
截止：明天 14:00

完成标准：
□ WASD移动
□ 摄像机跟随
□ 不穿墙
□ 可以打包运行

19. 任务不要写得太大

不要：

“做战斗系统”

拆成：

玩家攻击
敌人受伤
伤害计算
死亡
掉落
战斗 UI

每个任务尽量做到一个人 0.5～1 天可以完成。

八、会议频率

20. 正式会议

建议：每天一次 15～30 分钟站会，只回答三个问题：

昨天做了什么？
今天做什么？
有没有卡点？

21. 阶段会议

遇到重要节点再开长会：

  • 选题会议
  • MVP 确认
  • 第一版 Prototype
  • First Playable
  • Alpha
  • Beta
  • 最终提交

22. 紧急会议

只有出现以下情况才临时开：

  • 核心技术卡死
  • 玩法大改
  • 时间严重不足
  • 核心成员任务阻塞
  • 发现无法按期完成

原则：

能在群里解决的问题，不专门开会。

九、明确分工

23. 每个人确定主职 + 副职

例如：

成员主职副职
A程序系统设计
B程序工具
CTA / 特效Shader
D3D / 美术UI
E策划数值 / 关卡

24. 明确负责人制度

每个模块必须只有一个最终负责人：

战斗系统 → A
UI → B
VFX → C
角色 → D
关卡 → E

其他人可以协助，但：

最后谁负责验收，必须明确。

十、版本与备份

25. 每天保留稳定版本

  • main 永远可运行
  • 每天至少一个稳定 Build
  • Build 编号
  • 重要节点打 Git Tag
  • 每天备份项目
  • 提交前测试
  • 最终提交前冻结版本

建议：

v0.1 Prototype
v0.2 Core Loop
v0.5 Alpha
v0.8 Beta
v1.0 Final

十一、开发规范

26. 确定最低规范

  • 文件命名
  • GameObject 命名
  • Script 命名
  • Prefab 命名
  • Git Commit 规范
  • 文件夹结构
  • TODO 标记方式
  • Bug 提交方式

27. 禁止事项

  • 不提交 Unity 缓存文件
  • 不直接覆盖别人工作
  • 不偷偷修改核心架构
  • 不在最后一天第一次测试
  • 不因为“以后可能用到”无限加功能

十二、项目管理最重要的一条

28. 每天都要有一个“可玩的版本”

不要：

第1周：全部在做资源
第2周：全部在接系统
第3周：发现根本没串起来

应该：

Day 1
核心玩法 Prototype

Day 3
最小可玩版本

Day 7
完整核心循环

Day 12
Alpha

Day 16
Beta

最后几天
只修Bug + 打磨

十三、今晚会议最终必须产出的东西

会议结束前，必须确认：

  • 队名
  • 队长
  • 成员名单
  • Unity 版本
  • Git 仓库
  • 协作工具
  • 美术资源来源渠道
  • TA 工作方式
  • 策划文档位置
  • 任务看板
  • 分工
  • 会议频率
  • Git / 资源规范
  • 备份方案
  • 明天第一批任务

最后每个人必须说清楚

“我负责什么、明天第一件事做什么、明天结束前交付什么。”
